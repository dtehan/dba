## Critical Constraints

**Query Size Limits**: Every SQL query MUST use TOP 50 or fewer. Large unbounded queries will fail or overwhelm the system. Always aggregate or limit results.

**Safety Rules**:
- Do not execute the user's original query via base_readQuery before completing the EXPLAIN analysis. EXPLAIN first, always.
- Do not `SELECT *` from large tables for any diagnostic purpose. Use `SAMPLE`, `TOP N`, or aggregate queries.
- Do not suggest PI changes without first verifying the current PI from `SHOW TABLE` and measuring skew.
- Do not collect statistics on every column blindly — target join keys, filter columns, and PI columns only.
- Do not recommend a NUSI if EXPLAIN already shows the optimizer using it efficiently.
- Do not propose native function replacements for simple SELECT / filter / aggregation patterns that are already idiomatic SQL.
- ALL SQL output in the report is for copy-paste review only — never auto-execute DDL.

### Step 1 — Receive and Parse the Query

Before running any diagnostic queries:

1. Acknowledge receipt and identify the query's apparent purpose (e.g., aggregation, join-heavy report, point lookup, ML feature pipeline).
2. Extract and list all table references (database.table format).
3. Identify all join keys, filter columns, and GROUP BY / ORDER BY columns.
4. Note any obvious red flags on first read:
   - `SELECT *`
   - Functions wrapping filter columns (e.g., `EXTRACT(YEAR FROM date_col) = ...`)
   - Implicit type conversions in join predicates
   - Subqueries that could be CTEs
   - Missing explicit table aliases

Present this initial parse as a brief summary so the user can confirm the query is understood correctly before proceeding.

### Step 2 — Gather Schema Metadata

For every table referenced in the query, run the following diagnostics:

#### 2a. Table Definition

```sql
SHOW TABLE {database_name}.{table_name};
```

Capture:
- Primary Index column(s) and type (UNIQUE PI / NUPI)
- Partitioning expression (if any)
- SET vs MULTISET
- Column data types (watch for CHAR vs VARCHAR mismatches on join keys)

#### 2b. Row Count and Size

```sql
SELECT
    TableName,
    SUM(CurrentPerm) / 1e9 AS size_gb,
    SUM(CurrentPerm) / NULLIFZERO(COUNT(*)) AS avg_amp_bytes
FROM DBC.TableSizeV
WHERE DatabaseName = '{database_name}'
  AND TableName = '{table_name}'
GROUP BY TableName;
```

#### 2c. AMP Skew Check

```sql
SELECT TOP 50
    Vproc,
    CAST(CurrentPerm AS BIGINT) AS PermSpace
FROM DBC.TableSizeV
WHERE DatabaseName = '{database_name}'
  AND TableName = '{table_name}'
ORDER BY CurrentPerm DESC;
```

Flag any table where the max AMP storage exceeds 3× the average — that indicates a skewed PI.

#### 2d. Statistics Currency

```sql
SELECT TOP 50
    TRIM(ColumnName) AS ColumnName,
    StatsType,
    LastCollectTimestamp,
    SampleSizePct,
    CAST(UniqueValueCount AS BIGINT) AS UniqueValues
FROM DBC.StatsV
WHERE DatabaseName = '{database_name}'
  AND TableName = '{table_name}'
ORDER BY LastCollectTimestamp ASC;
```

Flag any column that:
- Has no stats entry but appears in a join or WHERE predicate (missing statistics)
- Has `LastCollectTimestamp` older than 30 days on a table that changes frequently (stale statistics)
- Has `SampleSizePct` < 10% on large tables (low sample may give inaccurate estimates)

#### 2e. Partition Index Check (PPI Tables)

```sql
SELECT TOP 20
    TRIM(DatabaseName) AS DatabaseName,
    TRIM(TableName) AS TableName,
    TRIM(ColumnName) AS ColumnName,
    IndexType, ColumnPosition
FROM DBC.IndicesV
WHERE DatabaseName = '{database_name}'
  AND TableName = '{table_name}'
  AND IndexType = 'Q'
ORDER BY ColumnPosition;
```

If the table has PPI and the partitioning column is not used in the query's WHERE clause, flag the missing partition elimination opportunity.

### Step 3 — Run EXPLAIN

Execute EXPLAIN before touching any data:

```sql
EXPLAIN {user_query};
```

If the query is complex (correlated subqueries, multi-level nesting, large intermediate cardinalities), also run:

```sql
DYNAMIC EXPLAIN {user_query};
```

#### 3a. Parse the EXPLAIN Output

Work through the plan step by step and tag each step using this rubric:

| Signal in EXPLAIN | Severity | Meaning |
|---|---|---|
| `estimated with no confidence` | Critical | Missing statistics — optimizer is guessing |
| `product join` | Critical | Potential Cartesian join — check join predicate |
| `all-rows scan` on table >1M rows | Critical | Full table scan — investigate PI filter and indexes |
| `(group_amps)` on very few AMPs | Critical | Severe data skew |
| `redistributed by hash code` with large spool | Warning | Expensive data movement — check PI alignment |
| `estimated with low confidence` on join/filter columns | Warning | Stale or partial statistics |
| Secondary index scan returning large result set | Warning | NUSI double-lookup overhead may exceed full scan cost |
| Multiple sequential redistributions | Warning | CTE restructure or pre-stage opportunity |
| Missing partition elimination on partitioned table | Warning | Partition column not in WHERE clause |
| `single-AMP RETRIEVE by way of the unique primary index` | OK | Best-case tactical access |
| `estimated with high confidence` | OK | Optimizer has reliable statistics |
| `duplicated on all AMPs` on a small table | OK | Correct broadcast strategy |
| `execute the following steps in parallel` | OK | Parallel dispatch confirmed |

#### 3b. Estimate Cost Impact

For each Critical or Warning item, estimate the relative cost:
- **High**: will materially degrade performance on tables >100M rows
- **Medium**: significant on tables 10M–100M rows
- **Low**: minor, but worth fixing for correctness

### Step 4 — Check DBQL for Actual Execution Metrics

If DBQL is enabled, query actual execution data for this query or similar patterns:

```sql
SELECT TOP 20
    QueryID, StartTime,
    CAST(TotalIOCount AS BIGINT) AS TotalIO,
    CAST(AMPCPUTime AS DECIMAL(18,2)) AS AMPCPUTime,
    CAST(SpoolUsage AS BIGINT) AS SpoolUsage,
    CAST(NumResultRows AS BIGINT) AS ResultRows,
    ErrorCode,
    CAST(TotalFirstRespTime AS DECIMAL(18,4)) AS ElapsedSec,
    NumSteps
FROM DBC.QryLogV
WHERE UserName = USER
  AND StartTime >= DATE - 7
ORDER BY AMPCPUTime DESC;
```

If this fails (DBQL not enabled or access denied), note it and continue with EXPLAIN-only analysis.

For the most resource-intensive matching query, check step-level details:

```sql
SELECT TOP 50
    StepNum, StepName,
    CAST(MaxAMPCPUTime AS DECIMAL(18,4)) AS MaxAMPCPU,
    CAST(AvgAMPCPUTime AS DECIMAL(18,4)) AS AvgAMPCPU,
    CAST(MaxAMPIO AS BIGINT) AS MaxAMPIO,
    CAST(MaxSpoolUsage AS BIGINT) AS MaxSpool,
    CAST(EstResultRows AS BIGINT) AS EstRows,
    CAST(ActResultRows AS BIGINT) AS ActRows
FROM DBC.QryLogStepsV
WHERE QueryID = {QUERY_ID}
ORDER BY StepNum;
```

Look for:
- **Estimation errors** — ActRows >> EstRows or ActRows << EstRows indicates missing or stale statistics
- **Step skew** — MaxAMPCPU >> AvgAMPCPU indicates data skew at that step
- **Large spool steps** — MaxSpool values consuming significant space

### Step 5 — Check Native Function Opportunities

Review the query against the mapping below. If hand-written SQL reimplements something Teradata does natively, flag it as a replacement opportunity.

| Hand-written Pattern | Native Function |
|---|---|
| Manual `AVG`, `STDDEV`, `COUNT` per column | `TD_ColumnSummary` |
| Manual percentile / histogram with CASE | `TD_UnivariateStatistics` / `TD_Histogram` |
| `(x - AVG) / STDDEV` Z-score logic | `TD_ScaleFit` + `TD_ScaleTransform` |
| Manual `COALESCE` / `UPDATE` for NULL fill | `TD_SimpleImputeFit` + `TD_SimpleImputeTransform` |
| CASE-based outlier detection | `TD_OutlierFilterFit` + `TD_OutlierFilterTransform` |
| Moving / rolling average with window functions | `TD_MovingAverage` |
| Manual Pearson correlation | `TD_Correlation` |
| External time series forecasting | `TD_ARIMAESTIMATE` → `TD_ARIMAFORECAST` (UAF) |
| Pairwise vector distance loops | `TD_VectorDistance` |
| LLM calls outside Teradata | `AI_AskLLM`, `AI_TextSummarize`, `AI_AnalyzeSentiment` |

If any apply, propose the rewritten version using the native function.

## Reference: EXPLAIN Phrase Glossary

| Phrase | Optimizer Intent |
|---|---|
| `single-AMP RETRIEVE by way of the unique primary index` | Best-case — no spool, no redistribution |
| `by way of an all-rows scan` | Full table scan — investigate predicates |
| `redistributed by hash code` | Row movement to co-locate join keys |
| `duplicated on all AMPs` | Broadcast of small table — check it is truly small |
| `(group_amps)` | Spool on subset of AMPs — potential skew |
| `(all_amps)` | Spool on every AMP — expected for large tables |
| `SORT to order Spool n by row hash` | Preparing for merge/hash join |
| `estimated with no confidence` | Missing statistics |
| `estimated with low confidence` | Stale or partial statistics |
| `estimated with high confidence` | Reliable optimizer estimates |
| `execute the following steps in parallel` | Concurrent independent steps — good |
| `hash join` | Standard large-table join |
| `merge join` | Sorted join — efficient when inputs pre-sorted |
| `product join` | Cartesian join — almost always a problem |
| `nested join` | Index-driven join — efficient for small outer inputs |
| `RowHash match scan` | Join driven by rowhash ordering |
| `eliminating duplicate rows` | DISTINCT or dedup in spool |

## Reference: Primary Index Design Rules

| Criteria | Good PI | Bad PI |
|---|---|---|
| Cardinality | High — many distinct values | Low — boolean, status, region |
| Join alignment | Matches the most frequent join key | Unrelated to join patterns |
| Skew | Even distribution across AMPs | >3× max/avg AMP ratio |
| Access pattern | Frequently filtered on this column | Rarely used in WHERE clauses |

Staging / load tables with unknown access patterns → use `NO PRIMARY INDEX`.
Session-scoped intermediates → use `CREATE VOLATILE TABLE ... WITH DATA ON COMMIT PRESERVE ROWS`.

## Reference: Statistics Collection Targets

Collect statistics on these columns, in priority order:

1. PI columns of all tables participating in joins
2. All join key columns (both sides of every join predicate)
3. All columns in WHERE clause predicates
4. Composite stats for correlated filter columns (e.g., `region` + `status` used together)
5. Partitioning columns on partitioned tables

Refresh frequency:
- After any load that changes >10% of rows
- At minimum monthly for high-traffic tables
- Use `USING SAMPLE N PERCENT` for very large tables to reduce collection cost
